OpenIncent

An open-source incentive-compensation engine. Turn a comp plan and deal data into per-payee commission payouts — with a full, immutable audit trail that explains every number.

Introduction

OpenIncent computes sales and recruiter commissions from three inputs you control:

  1. A plan — your comp rules, written in YAML (or drafted from plain English by the AI builder).
  2. Transactions — your deals/placements, as CSV, Excel, or Parquet. Messy column names are fuzzy-matched automatically.
  3. Payees — your reps/recruiters and their quotas.

You get back explained payouts: per-rep statements (XLSX, HTML, PDF) and an audit ledger that traces every dollar to the exact rule and deal behind it. Everything is computed in exact decimal arithmetic — no floating-point drift — and is deterministic: the same inputs always produce byte-identical output.

Who it's forTeams whose comp has outgrown a spreadsheet but doesn't justify a full RevOps hire or a per-seat SaaS subscription. Splits, tiers, accelerators, draws, clawbacks, manager overrides, team quotas, contract-margin commission — all handled. Not for tiny teams perfectly happy in a spreadsheet.

OpenIncent runs entirely on your machine. There is no cloud, no account, and your data never has to leave your computer. It is licensed AGPL-3.0 — run it, modify it, and self-host it freely.

Quickstart (5 minutes)

Three small files and one command.

1 · plan.yaml

plan_id: starter
name: "Starter Plan"
period_type: monthly
currency: USD
rules:
  - id: base_commission
    type: flat_rate
    rate: 0.05          # 5% of every deal

2 · reps.csv

id,name,quota,plan_id,effective_from
R1,Alice,100000,starter,2026-01-01
R2,Bob,100000,starter,2026-01-01

3 · deals.csv

id,payee_id,amount,period
D1,R1,20000,2026-01
D2,R2,12000,2026-01

4 · Run it

icm --plan plan.yaml --transactions deals.csv --payees reps.csv --output out/

You'll get commission and summary files in out/. Alice earns 1,000.00 (5% of 20,000); Bob earns 600.00. To produce per-rep statements and see the full explanation, read Statements & output and Audit trail.

No plan yet?Run icm plan-from-text "reps get 5% on every deal, 8% above quota" to draft a validated plan YAML from a plain-English description. (Needs an LLM API key — set ANTHROPIC_API_KEY.)

Core concepts

TermMeaning
PlanThe set of rules that turn deals into commission, plus period type, currency, caps, draws, and rounding. One plan per payee (different payees can be on different plans in the same run).
PayeeA person who earns — rep, recruiter, manager. Has a quota (and optionally time-varying quotas, a ramp, a draw, a manager, a team).
TransactionA deal/placement. Carries an amount (and, for margin plans, bill/pay rates or a margin). May be split across payees via credits.
PeriodThe payout window — monthly, quarterly, or annual. Transactions carry a period (YYYY-MM) or a close_date the period is derived from.
AttainmentBookings ÷ quota for a payee in a window. Drives tiered rates, accelerators, and minimum-attainment gates.
CreditHow a deal is allocated: a split (shares that sum to 100%) or an overlay (additive, e.g. a manager override).
Audit ledgerAn immutable record of every decision point — filter, tier crossing, cap, draw, adjustment — so any number can be explained without recomputation.

The plan (YAML)

A plan is a YAML document. Top-level fields:

FieldRequiredDescription
plan_idyesUnique identifier. Payees reference it via their plan_id.
nameyesHuman-readable name (appears on statements).
period_typeyesmonthly · quarterly · annual.
currencyyesISO code, e.g. USD. Internal calculation currency.
rulesyesA list of rules (see Rule types). Evaluated in order.
reporting_currencynoIf set and different from currency, output is converted for display only. Blank = no conversion.
payout_capnoMaximum total payout per payee per period (applied after rules).
drawnoPlan-wide draw/guarantee (see Draws). Can also be set per payee.
pro_ratingnofull (default) · daily · zero — how partial periods pro-rate quota.
roundingnoDisplay rounding policy (see Rounding). Default: exact.

Rule types

Every rule has an id, a type, and these optional modifiers:

ModifierDescription
filterOnly apply to matching transactions (see Filters).
capMaximum commission this rule can pay per payee per period.
min_attainment_pctGate: skip a payee below this attainment (e.g. 0.5 = below 50% of quota earns nothing from this rule).
quota_categoryMeasure attainment against a category-specific quota (see category quotas).
baseamount (default) or margin — what the rate applies to (see Margin).

flat_rate

A constant rate on the base.

- id: perm_fee
  type: flat_rate
  rate: 0.10            # 10% of each placement fee

tiered

Rates that change as cumulative attainment crosses thresholds. Boundary-crossing: a single deal that straddles a threshold is automatically split, each slice paid at its tier's rate. threshold_pct is expressed as a fraction of quota — 1.0 = 100%. Tiers must ascend by threshold_pct.

- id: tiered_core
  type: tiered
  tiers:
    - threshold_pct: 1.0    # 0–100% of quota
      rate: 0.05
    - threshold_pct: 1.5    # 100–150% of quota
      rate: 0.08
    - threshold_pct: 100.0  # everything above 150%
      rate: 0.12
Why "100.0" on the top tier?It's just a threshold high enough that all remaining attainment falls into it. Any deal above the previous boundary is paid at the top rate.

accelerator

Pays rate × multiplier on the portion of bookings above a threshold (a fraction of quota). It pays on the excess only, so it's normally paired with a flat_rate rule that pays the base on everything.

rules:
  - id: base_flat
    type: flat_rate
    rate: 0.05             # base 5% on everything
  - id: over_quota_kicker
    type: accelerator
    rate: 0.05
    threshold_pct: 1.0     # above 100% of quota
    multiplier: 2.0        # the excess pays 0.05 × 2.0 = 10%

A plan can combine rules — e.g. a tiered core plus a product SPIF:

rules:
  - id: tiered_core
    type: tiered
    tiers: [{threshold_pct: 1.0, rate: 0.05}, {threshold_pct: 100.0, rate: 0.10}]
  - id: enterprise_spif
    type: flat_rate
    rate: 0.02
    filter: 'product == "Enterprise"'

Crediting & splits

By default a deal credits its payee_id at 100%. To split a deal across recruiters — the staffing "180/360 desk split" — add a credits column to the transaction. Four forms are accepted:

FormExampleMeaning
CompactR1:0.6;R2:0.4R1 gets 60%, R2 gets 40%.
PercentR1:60%;R2:40%Same as above.
OverlayR1:1.0;M1:0.1@overlayR1 gets 100%; M1 gets an additive 10% override.
JSON[{"payee_id":"R1","split_pct":"0.6"},…]Explicit form.
Splits must sum to 100%The split credits on a deal must total exactly 1.0, or that row is reported as an error. Overlays are additive and don't count toward the 100%.

Manager overrides can also be generated automatically: give a payee a manager_id and a manager_override rate, and the engine adds an overlay credit up the reporting chain — no per-deal markup needed.

Margin / gross profit staffing

Contract and temp desks pay recruiters on gross profit (margin), not the full bill. Set base: margin on a rule and provide the margin on each transaction — either as per-unit rates or a direct figure:

# Plan
- id: gp_commission
  type: flat_rate
  base: margin
  rate: 0.10           # 10% of gross profit
# deals.csv — margin from rates × hours
id,payee_id,period,bill_rate,pay_rate,units
D1,R1,2026-06,85,60,160      # GP = (85 − 60) × 160 = 4,000 → commission 400

# …or a direct margin column
id,payee_id,period,margin
D2,R1,2026-06,4000

Margin works with all three rule types — including tiered (intra-deal threshold splitting on gross profit) and accelerators. For tiered/accelerator margin plans, attainment is measured in margin, and the quota is read as a gross-profit target. A row that has no margin data is skipped and recorded in the ledger (it never aborts the run).

margin precedenceIf a margin column is present it is used directly; otherwise margin is computed as (bill_rate − pay_rate) × units, where units defaults to 1.

Filters

A rule's filter is a small expression that decides which transactions it applies to. It can reference canonical fields, margin fields, and any extra (metadata) column in your file.

filter: 'product == "Enterprise"'
filter: 'amount > 50000 and region == "EMEA"'
filter: 'product in ["Pro", "Enterprise"] or deal_type != "Renewal"'
filter: 'margin > 1000'
filter: '`Deal Type` == "New"'    # back-ticks for column names with spaces
Operators== != > < >= <= in [ … ]
Logicand, or, parentheses
ValuesStrings in quotes; numbers bare; dates as "YYYY-MM-DD"
Fieldsid, payee_id, deal_id, period, amount, product, close_date, margin, bill_rate, pay_rate, units, plus any metadata column
Missing fieldsA field absent from a row is treated as "not equal" to any value: != matches it; ==, ordering, and in do not. A filter that fails to parse is reported with a clear message rather than silently matching nothing.

Draws, ramps & quotas

Draws / guarantees

A draw guarantees a minimum payout per period. Non-recoverable is a simple floor; recoverable advances are recovered from future earnings (the balance is threaded across periods).

# In the plan (plan-wide) or per payee
draw:
  amount: 3000
  recoverable: true

In a payees CSV, set columns draw_amount and draw_recoverable (true/yes/y/1/on).

Ramp schedules (new-hire quota relief)

Give a new recruiter reduced effective quota for their first months. In the payees file: ramp_months and a space-separated ramp_schedule of multipliers.

id,name,quota,plan_id,effective_from,ramp_months,ramp_schedule
R9,New Recruiter,100000,starter,2026-06-01,3,0.50 0.75 1.0

Time-varying quotas

Add a period column to the payees file and one row per period to set per-period quotas; the row without a period sets the default.

Category quotas

A payee can carry a JSON category_quotas map; a rule with a matching quota_category measures attainment against that category's quota instead of the overall one.

Team / shared quotas

Give payees the same team_id and their bookings and quotas pool — every member sees the team's combined attainment %.

Rounding & currency

Calculation is always exact decimal. Rounding and currency conversion are applied only at the display boundary — they never feed back into the math.

rounding:
  mode: half-up      # half-up · half-even · floor · ceil · none
  places: 2          # 0–6 decimal places

With a policy set, statement and API line items are rounded, and totals equal the sum of the rounded lines (so a statement reconciles to the penny against its own rows). For multi-currency display, set reporting_currency on the plan and provide exchange rates; amounts are converted for output only.

Transactions file

CSV, XLSX, or Parquet. Column names are fuzzy-matched, so Consultant, Sales Rep, or Owner all map to payee_id. Canonical fields:

FieldNotes
idTransaction id. Auto-generated if absent.
payee_idWho the deal credits (unless overridden by credits).
deal_idOptional grouping id (defaults to id).
periodYYYY-MM. If absent, derived from close_date.
amountDeal value. May be negative (refunds / clawbacks).
productOptional; usable in filters.
close_dateOptional; used to derive period.
bill_rate,pay_rate,units,marginFor margin plans (see Margin).
creditsSplit/overlay allocation (see Crediting).
any other columnKept as metadata and usable in filters.
ClawbacksRepresent a fall-through or refund as a transaction with a negative amount (or negative margin) in the period you're recovering it. The audit trail labels it automatically on statements.

Worked example: a contract desk split staffing

One contract placement, paid on gross profit, split between a sales and a delivery recruiter — margin and splits together, end to end.

plan.yaml

plan_id: contract_desk
name: "Contract Desk - GP split"
period_type: monthly
currency: USD
rounding: {mode: half-up, places: 2}
rules:
  - id: gp_commission
    type: flat_rate
    base: margin
    rate: 0.15             # 15% of gross profit

reps.csv

id,name,quota,plan_id,effective_from
S1,Sales Sam,0,contract_desk,2026-01-01
D1,Delivery Dana,0,contract_desk,2026-01-01

deals.csv

id,payee_id,period,bill_rate,pay_rate,units,credits
P100,S1,2026-06,100,70,160,"S1:0.6;D1:0.4"

Run

icm --plan plan.yaml --transactions deals.csv --payees reps.csv --output out/ --csv
icm statements --plan plan.yaml --transactions deals.csv --payees reps.csv \
    --output out/ --period 2026-06 --format html

The numbers

Gross profit on the placement is (100 − 70) × 160 = 4,800. The credits split it 60/40, and each share is paid at 15%:

RecruiterMargin shareRateCommission
S1 (sales)4,800 × 0.60 = 2,880.0015%432.00
D1 (delivery)4,800 × 0.40 = 1,920.0015%288.00
Total720.00

Open out/statement_S1_2026-06.html and click the line to see the same arithmetic spelled out — that's the explanation you hand a recruiter who asks "why 432?"

VerifiedRunning these exact files produces S1 = 432.00, D1 = 288.00, total 720.00 — reconciled to the cent.

Statements & output

A calculate run writes a commissions file and a per-payee summary to --output. To produce client-ready statements:

icm statements --plan plan.yaml --transactions deals.csv --payees reps.csv \
    --output statements/ --format html,xlsx,pdf

Each payee gets one file containing only their own data — every line item, the rule and rate that paid it, adjustments labelled (clawback, true-up, cap, draw, manual), and a reconciled total. HTML statements are interactive: click a line to expand the calculation. Statements honour the plan's rounding policy and, if set, the reporting currency.

Branding (--theme)

Statements can carry your company's look: name, logo, accent colour, currency symbol, labels, and footer lines. Keep a theme.yaml next to your plan and pass it on the command line — with no theme, statements use the plain built-in style (currency symbol inferred from the plan's currency).

# theme.yaml — every field optional
company_name: Meridian Search Group
logo_url: logo.png            # URL, relative path, or data URI
accent_color: "#0e7490"
currency_symbol: "£"
contact_line: "Questions? Email comp@meridian.example"
footer_note: "Paid via April payroll"
show_attainment: true         # quota progress bar on/off
show_line_explanations: true  # plain-English math under each deal
show_powered_by: false        # hide "Generated by OpenIncent"
icm statements --plan plan.yaml --transactions deals.csv --payees reps.csv \
    --output statements/ --format html,pdf --theme theme.yaml
Period locking & true-upsLock a period once it's paid; if late deals arrive, recalculating produces only the deltas (true-ups and clawbacks) against the locked baseline — not a full re-pay. Locking a period also generates a finance payout register.

Audit trail & trace

Every run records an immutable ledger of decision points: which filter matched, where a tiered deal crossed a threshold, why a row was skipped, when a cap or draw applied. This is what ends commission disputes — you can explain any number without recomputing anything.

icm trace --txn D1 --payee R1

The trace shows how one deal moved through each rule for that payee — matched or skipped, the events at each step, and the resulting commission — in plain language (a tiered slice reads like $300,000 of this deal fell between 100% and 125% attainment → 11.148%). The same ledger backs the interactive HTML statements, so a recruiter's "why did I earn this?" is answered before they ask. (Trace reads the saved ledger, so it works after a normal run — not with --no-db.)

HTTP API

For programmatic use or the desktop UI, run a local API:

icm serve        # FastAPI, local only by default

The main endpoint, POST /v1/calculate, accepts the plan, transactions, and payees as multipart files and returns commissions, the per-payee summary, the audit ledger, attainment, and draw balances as JSON. Money values are returned as exact decimal strings (never floats). Rounding policy from the plan is applied to the response. Additional endpoints cover file preview/mapping, saved plans and rosters, and statement export.

FAQ & troubleshooting

"Split credits must sum to 1.0"

A deal's credits splits don't total 100%. Check the row named in the error. Overlays (@overlay) are additive and excluded from the 100%.

A margin rule paid nothing for some deals

Those rows had no margin data (bill_rate/pay_rate/units or margin). They're skipped and recorded in the ledger as no_margin_data rather than aborting the run — check your input columns.

A rep earned nothing from a rule

Likely a min_attainment_pct gate (below threshold), a filter that excluded their deals, or a zero quota. icm trace shows exactly which.

"Invalid rule filter …"

The filter expression didn't parse — check quotes around string values and back-ticks around column names with spaces. The message includes the offending expression.

Are amounts exact?

Yes — all calculation is decimal, no floating point. Rounding is display-only and configurable; a statement's lines always sum to its shown total.

Does my data leave my machine?

No. The engine runs locally; there's no cloud and no account. The database is a local SQLite file.
